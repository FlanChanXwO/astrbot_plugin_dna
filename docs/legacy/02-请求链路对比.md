# 官方客户端与服务端请求链路对比

## 已对齐部分

官方 App 的短信接口为 `POST user/getSmsCode`，使用表单字段：`mobile`、`vJson`、`isCaptcha=1`。登录接口为 `POST user/sdkLogin`，包含 `loginType`、`sdkToken`、`code`、`gameList` 与 `mobile`。

服务端实现已按 APK 静态代码修正以下事项：

- 使用 App 对应的接口和字段形状；登录请求不额外提交 `devCode` 表单字段。
- 对齐 `sa`、`tn` 与请求随机数的签名行为。
- 使用客户端版本、平台和设备相关头字段的等价格式。
- 使用 `2` 加 32 位十六进制的 App `devCode` 结构。

因此，已知失败不应归因于接口路径、手机号字段、验证码字段或签名字段的明显遗漏。

## 仍不可由服务器复刻的差异

| 维度 | 官方 App | DNAUID 服务端 | 影响 |
| --- | --- | --- | --- |
| `devCode` 来源 | Android 设备标识派生并长期稳定 | 服务端生成或保存的标识 | 短信码与登录请求必须使用同一身份。 |
| 验证码 | App 内阿里云原生 SDK 实时生成 | 浏览器中完成后由服务端转发 | 验证结果可能关联浏览器、SDK、会话或网络上下文。 |
| 网络栈 | Android App 进程直接出站 | Linux 服务进程出站 | 出口地址、TLS 特征及系统环境不同。 |
| 设备环境 | 真实运行时属性和 SDK 状态 | 只能构造请求字段 | 请求头相同不等于运行环境相同。 |

## 关键绑定关系

对照测试表明：官方 App 发出的短信验证码，只有使用同一 App 的 `devCode` 才能完成 `sdkLogin`。将验证码与服务端临时 `devCode` 混用时，上游返回 `151`。

这说明 `devCode` 不是主要功能的日常必需字段，但它是 App 短信登录链路的身份关联材料。
