# 2026-08-06：Native 会话参数突破（248 根因确认与完整方案）

## 结论

`248` 的根因是 **ct4.js 初始化缺少 native 会话参数**（`clientType: android`、`mi`、`rem`）。补齐后，第三方客户端（包括桌面浏览器）产出的验证码 vJson 即可被后端接受，`getSmsCode` 返回 `200`。

**服务端方案完全可行，无需导出 App。** 完整链路已在桌面浏览器端到端验证：发码 → 输码 → `sdkLogin` → 拿到 `token` + `refreshToken`。

---

## 之前为什么失败（248 的成因）

历史上的服务端代发短信反复得到 `248`，原因可以归纳为三条叠加：

### 1. 用了 Web 会话的验证码，而不是 App 会话

- 插件 Web 登录页用的是 **Web 场景 captchaId** `b4b05ab6ca764ef4242e87cba47df9c8`。
- 官方 App 用的是 **App 场景 captchaId** `114d4e96cc4536050c7efaeb7e4f3c8c`（APK 硬编码 + `config/switchAll` 服务端下发一致）。
- 用户在浏览器完成 Web 场景验证码得到的 vJson，后端用 App 场景的 appKey 调阿里云校验时**无法通过** → 泛化为 `248 网络异常`。

### 2. 即便用了 App 场景，也缺少 native 会话参数

- 若只把 captchaId 换成 App 场景，仍会 248：官方原生 SDK 除了 captchaId，还会向 ct4.js 传入
  `clientType: 'android'`、`clientVersion: '1.8.4'`、`outside: true`、`rem: 0.85`、`mi: {packageName, appVer, build, geeid}`。
- 这些参数决定验证码会话是"native 类型"。缺失时 ct4.js 走 web 会话，产出的 vJson 与 App 场景不匹配 → 248。
- 之前所有服务端复测（字段/签名完全对齐）都缺这一层，所以始终 248。

### 3. 辅助性假因（已被本轮排除）

| 曾怀疑的假因 | 结论 |
| --- | --- |
| captchaId 本身 | 不是；换 App captchaId 后仍需 native 参数 |
| 包名/签名证书绑定 | 不是；任意外部包名 `com.dnabridge.dna_bridge` 同样 200 |
| GeeGuard 设备风控 | 不是；官方 APK 未打包 GeeGuard 类（反射返回 null，无 GeeToken） |
| TLS/HTTP 客户端指纹 | 不是；Python urllib、Dart、Android WebView、桌面浏览器均可 |
| devCode 派生（Android ID vs 随机） | 不是；随机 `"2"+32hex` 即满足格式与一致性 |
| 网络出口/IP | 不是；atri、宿主机、模拟器、桌面均成功（在参数正确后） |

另外注意：`151 错误手机号` 是 **devCode 绑定校验** 的泛化文案（发码与登录必须同一 devCode），不是号码格式错误。之前多用户方案里把它误当号码问题。

## 这次为什么成功

### 定位过程（2026-08-06）

1. **确认 App 场景 captchaId**：反编译 APK 得 `CAPT_CHA = 114d4e96cc4536050c7efaeb7e4f3c8c`，`config/switchAll` 返回一致。
2. **用真实 vJson 做隔离测试**：模拟器 WebView 完成验证码 → vJson 提交仍 248；官方 App 原生 vJson 经同一管线提交 → **200**。定位到"vJson 生成会话"这一层。
3. **抓取官方 gt4 页面参数**：官方 App WebView 可调试，抓到 `gt4-index-alicom.html?data=<json>`，内含 `challenge`、`clientType`、`mi`、`rem` 等 native 参数。
4. **复刻参数**：在 WebView/桌面浏览器的 `initAlicom4` 配置中补上 `clientType/android` + `mi`（包名任意）+ `rem` → vJson 被接受。

### 端到端验证

`script/` 独立测试页（`server.py` 复用 DNAUID 签名逻辑 + `login.html`）在桌面浏览器：
- 完成 App 场景验证码（native 参数）→ vJson 提交 `getSmsCode` → **200**（短信发出）。
- 用户输码 → `sdkLogin` → **成功**，拿到 `token` + `refreshToken`。
- 关键前提：**发码与登录用同一 devCode**（cookie 会话持久化），否则 `151`。

### 为什么原生 SDK 与 Web 页能等价

- 官方原生 SDK 的验证码本质上就是 **WebView + ct4.js**（加载内置 `gt4-index-alicom.html`）。
- 两者都调 `initAlicom4`，差异只在传入参数。补齐 native 参数后，Web 页与原生 SDK 产出等价的 native 会话 vJson。
- GeeGuard 未打包 → 无额外设备风控层。

## 关键参数（落地用）

`initAlicom4` 配置：

```json
{
  "captchaId": "114d4e96cc4536050c7efaeb7e4f3c8c",
  "https": true,
  "product": "bind",
  "clientType": "android",
  "clientVersion": "1.8.4",
  "outside": true,
  "rem": 0.85,
  "mi": {
    "packageName": "com.dnabridge.dna_bridge",
    "displayName": "DNA登录桥",
    "appVer": "0.1.0",
    "build": "1",
    "clientVersion": "1.8.4",
    "geeid": { "bd": "$unknown", "d": "$unknown", "e": "$unknown", "ver": "1.0.0", "client_type": "android" }
  }
}
```

- 包名/版本/指纹均可任填（未被严格校验）。
- 桌面浏览器与 Android WebView 均可用。

## 反证排除

- 伪造 vJson：`captcha_output` 由阿里云服务端用场景 appKey 密钥签名，客户端无法伪造。
- 重放：`lot_number`/`pass_token` 一次性 + `gen_time` 时效。
- Web 会话（缺 native 参数）：248。

## 对插件的落地改动（待实施）

1. `templates/index.html.j2`：captchaId 换 App 场景 + `initAlicom4` 加 native 参数。
2. 服务端 `getSmsCode` 请求补 `isCaptcha=1` 字段（与 App 路径一致）。
3. 发码与 `sdkLogin` 用同一会话 devCode（插件已有 `web_dev_code` 机制）。

## 风险与边界

- 长期稳定性：阿里云/皎皎角可能收紧对非官方客户端的 native 会话校验。
- 方案让用户在自己的浏览器完成验证码、服务端代发短信并登录，未绕过真人交互；仍在官方登录协议合理边界内。
- 若上游未来开放正式扫码/OAuth，应优先迁移。
