# `248` 与安全客户端设计

## 结论先行

`248` 是上游后端在 HTTP 成功响应中作出的业务拒绝，不是 DNAUID 容器无法联网的证据，也不能仅凭该码断言为上游服务故障。

本次对照中，官方原生 App 可完成验证码并进入输入验证码状态；服务端独立复测即使已对齐版本、公开设备声明、请求字段和签名形态，仍收到 `248`。因此更准确的描述是：上游后端拒绝了非官方客户端上下文的发码请求，但未向客户端公开具体触发规则。

## “后端拒绝”不等于“后端有缺陷”

后端负责决定是否发送短信，故 `248` 的最终决定发生在后端。然而，验证码、设备和反滥用校验通常本就是后端的安全职责。若该规则有意要求官方客户端上下文，则对服务器仿真请求的拒绝是预期安全行为，不足以认定为服务端 bug。

只有在官方原生 App 于正常网络下也持续收到相同错误，或官方明确声明服务端接口应允许第三方服务器调用时，才有理由将其优先判断为后端故障或兼容性事故。

## 后端可能使用的环境信号

| 信号类别 | 本次证据 | 可能用途 | 置信度 |
| --- | --- | --- | --- |
| 验证码回执 `vJson` | App 把 Alicom 原生 SDK 成功回执原样提交；网页验证回执并非原生 SDK 产生 | 验证挑战、会话、时效及回执签名 | 高：存在该差异；中：具体绑定规则未公开 |
| 持久化 `devCode` | APK 首次启动后由 Android ID 派生并保存；服务端独立复测未拥有该设备的既有值 | 设备一致性、账号/验证码绑定、风控历史 | 高：实现已确认；中：是否为本次拒绝主因未知 |
| 请求签名与动态配置 | APK 使用服务端下发的加密列表、请求密钥和 `tn`/`sa` 签名 | 防篡改、时效与协议版本控制 | 高 |
| Cookie/服务端会话 | App 配置了 CookieJar；验证码 SDK 可能另有服务端会话 | 关联挑战完成与后续发码请求 | 中 |
| 网络出口与信誉 | 官方 App 和 `atri` 服务器不是同一出口；用户反馈不能证明所有出口都无差异 | IP、ASN、地域、速率、黑名单或代理风险 | 中：可作为信号；低：是否触发 `248` 未验证 |
| TLS / HTTP 客户端指纹 | 官方为 Android WebView/OkHttp，服务端复测为 Python/OpenSSL | 将请求与受支持客户端族关联 | 中：差异存在；低：服务端是否使用该信号未知 |
| 交互与设备风险 | 原生 SDK 可收集自己的运行环境信息 | 防自动化、防批量发码和设备风险评分 | 低到中：符合常见设计，未获得服务端规则 |

以上是风险信号集合，不是已证实的单一规则。`248` 很可能是风控系统的泛化错误文案；不能从一个错误码反推出权重、阈值或绕过方法。

## 为什么公开头字段并不足够

`version`、`model`、`osVersion`、`User-Agent` 等字段由客户端上报，容易被伪造，通常只适合作为低可信特征。可靠校验会把它们与挑战回执、服务器会话、设备长期状态、请求节奏和网络风险结合判定。

这解释了本次现象：公开字段和签名形态对齐后，服务器仍能基于未公开或不可伪造的上下文拒绝请求；官方 App 成功则表明该上下文在原生链路中成立。

## 能否复刻“这样的安全 App”

可以为**自有后端**构建同类安全登录 App；不能把第三方 App 的验证码回执、设备身份或环境校验复刻成等价客户端，除非获得对方提供的正式 SDK、服务端契约和授权。

面向自有系统，建议采用以下设计：

1. 由后端签发一次性、短时有效的登录挑战，并把挑战与用户操作会话绑定。
2. 使用 Android Keystore 生成每设备密钥对；客户端对挑战签名，服务端保存公钥及设备状态。不要把可伪造的设备码当作唯一安全依据。
3. 将验证码服务商的官方 SDK 回执直接交给自有后端验证；回执、验证码和 refresh token 不落日志。
4. 在服务端按账号、设备、IP/ASN、挑战时效和发送频率做可解释的风控决策，并返回可区分的错误类别给受信客户端。
5. 使用短期 access token 与可撤销的 refresh token；凭证续期与再次人工登录分开处理。
6. 为误判提供申诉或可信设备恢复路径，避免把“网络异常”作为所有拒绝的统一文案。

## 本案可行边界

DNAUID 目前应继续使用已经保存的凭证与 refresh token 续期。首次登录或凭证完全失效后的重新授权，需要让用户在官方 App 内完成。若上游未来提供正式扫码、OAuth 或设备授权接口，应优先迁移到该协议。

不建议继续扩大服务器仿真、提取原生验证码回执或改变客户端指纹来尝试通过 `248`；这些做法既不稳定，也会突破上游的反滥用边界。

## 当前安全等级判断

仅根据本次 APK 静态分析、授权模拟器对照和受控服务端响应，可作如下分层判断：

| 维度 | 判断 | 依据与限制 |
| --- | --- | --- |
| 短信发码反滥用 | 中等偏高 | 原生验证码 SDK、动态签名/配置及服务端环境拒绝共同生效；已能阻止简单的服务器字段仿真。 |
| 设备绑定 | 中等 | `devCode` 稳定但由 Android ID 派生，不是不可导出的硬件私钥证明。是否还有服务端设备画像未知。 |
| 客户端抗逆向 | 中等偏低 | APK 经过混淆但登录流程、请求头和签名入口仍可静态定位；客户端代码本身不能作为信任边界。 |
| 整体登录安全 | 中等 | 对普通批量发码/脚本攻击有效；没有证据证明使用硬件证明、平台完整性校验、强证书锁定或金融级交易签名。 |

“服务器仿真得到 `248`”仅证明后端掌握了客户端之外的有效校验条件，不证明每一层都达到高安全等级。对抗已控制真实设备的 Hook、自动化或转发，仍需依赖服务端设备撤销、行为风控和高风险操作的二次验证。
