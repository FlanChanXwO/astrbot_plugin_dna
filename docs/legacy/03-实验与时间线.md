# 实验与时间线

## 初始现象

1. 用户选择 App 登录。
2. DNAUID 调用登录接口后收到上游 `151`，提示手机号错误。
3. 官方 App 可完成验证码并成功发出短信，说明测试账号和官方客户端链路可用。

## 协议修正与对照

1. 依据 APK 静态实现修正 App 请求字段、版本头、`devCode` 格式及签名随机数。
2. 使用官方 App 设备对应的 `devCode` 和新鲜短信验证码执行最小登录验证，得到成功响应（`200`）。
3. 使用服务端生成的不同 `devCode` 搭配同一来源短信验证码，登录被拒绝（`151`）。

结论：验证码与发码设备身份存在绑定，先前的“错误手机号”是该绑定失败的泛化提示，而非号码格式错误。

## 尝试服务端自动发码

为保证发码与登录使用同一 `devCode`，曾恢复服务端代发 App 短信的路由，并保存会话内设备码。浏览器到 DNAUID 的请求正常到达，随后 DNAUID 调用上游 `user/getSmsCode` 返回：

```text
code=248
msg=网络异常，请稍后重试
```

无本地 `aiohttp` 异常或容器网络异常日志。上游未返回更细的拒绝理由，因此不能将其确定归因于单一字段或单一 IP。

## 2026-07-31：字段与签名对齐后的独立复测

为排除旧版插件的实现差异，建立了一个仅监听本机、仅用于一次发码验证的临时调试页。用户在页内自行填写号码并完成人机验证；页面和服务端日志均不记录号码、验证码、验证回执或设备标识。

该请求已按当前 APK 的静态实现对齐：

1. `user/getSmsCode` 的三个表单字段：`mobile`、`vJson`、`isCaptcha=1`。
2. App 的版本、版本号、系统信息、语言/地区、请求头及 `tn`/`sa` 签名结构。
3. 16 位数字请求随机数、时间戳与加密公钥处理。

上游仍以 HTTP `200` 返回业务码 `248`（“网络异常，请稍后重试”）。因此，旧版 DNAUID 中的字段偏差、旧 `devCode` UUID 形态和签名随机数形态并非 `248` 的唯一原因。

静态代码同时确认了仍未能够等价复现的上下文：

1. `devCode` 是 App 首次启动时由 Android ID 派生并持久化的设备标识，不是每次请求新建的 UUID。
2. App 使用 Alicom 原生验证码 SDK；SDK 成功回调的原始字符串直接作为 `vJson` 上送。网页 `ct4.js` 虽使用同一验证码 ID，但产生于桌面浏览器环境，不能证明与原生 SDK 回执等价。
3. 请求仍从服务器的 Python/OpenSSL TLS 栈发出，不是 Android WebView/OkHttp/Conscrypt 栈。

复测没有再次尝试，也没有获得可运行 Android 模拟器的 ADB 连接，故不能把 `248` 单独归因于上述任一项。

## 2026-07-31：原生客户端动态对照

随后连接到授权 Android 模拟器，确认其中安装的是同一包名、同一版本的 APK，且公开系统参数与独立复测中使用的 App 声明一致。应用为非调试版本，`run-as` 被系统拒绝，未读取其私有偏好设置或设备标识。

用户在官方 App 内自行触发一次发送验证码并完成验证码挑战。脱敏日志显示原生 Alicom SDK 成功回调，界面随后进入“输入验证码 / 重新发送”状态，表明官方原生链路已经成功发码。本轮未读取或保存号码、验证码、`vJson`、token 或 `devCode` 原值。

该动态对照将结论收敛为：同一 APK 版本与基础公开设备声明并不导致 `248`；服务器侧仍缺少原生验证码 SDK 的回执上下文、持久化设备身份和 Android 客户端传输/出口环境中的一个或多个前置条件。由于这些是服务端反滥用边界，本记录不尝试提取、重放或伪造回执。

## 现有凭证验证

用户确认先前保存的凭证仍可驱动主要功能。该事实将故障范围限定为“首次/重新登录”，而非已登录账号的常规接口访问。

## 2026-08-06：Native 会话参数突破

详见 [08-2026-08-06-native会话参数突破](08-2026-08-06-native会话参数突破.md)。要点：

1. 反编译 APK 确认 App 场景 captchaId = `114d4e96cc4536050c7efaeb7e4f3c8c`（`config/switchAll` 下发一致）。
2. 隔离测试证明：官方 App 原生 vJson 经第三方管线提交 → 200；WebView/Web 会话 vJson → 248。差异在 vJson 生成会话。
3. 抓取官方 gt4 页面参数，确认缺 `clientType/android` + `mi` + `rem` 等 native 参数。
4. 补齐参数后，桌面浏览器 + 独立测试页完成完整登录：`getSmsCode` 200 → `sdkLogin` 成功 → 拿到 token。
5. 排除了包名绑定、GeeGuard、TLS 指纹、devCode 派生、网络出口等此前怀疑的假因。
