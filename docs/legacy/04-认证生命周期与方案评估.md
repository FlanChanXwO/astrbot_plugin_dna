# 认证生命周期与方案评估

## 官方客户端能力

APK 登录界面静态代码显示两种路径：

1. 短信验证码登录。
2. 运营商一键登录：由终端运营商 SDK 生成临时 `sdkToken`，再调用 `sdkLogin`。

未发现该登录界面使用扫码登录、OAuth 回调或可由第三方网页接入的授权码流程。一键登录依赖用户终端的 SIM、运营商网络和 SDK，不能安全地移植到服务器。

## 已有续期能力

官方客户端登录响应包含 `refreshToken`，并调用 `POST user/refreshToken` 更新短期 token。DNAUID 当前数据模型同样保存 App/Web 的 `refresh_token`，并在适当的凭据检查路径中调用该接口。

含义是：

- 普通 access token 到期不必等同于重新短信登录。
- refresh token 被撤销、过期或账号被官方强制下线时，仍需重新授权。
- 旧记录若没有保存 refresh token，则不具备自动续期条件。

## 多用户方案结论

| 方案 | 首次接入 | 日常续期 | 多用户成本 | 结论 |
| --- | --- | --- | --- | --- |
| 服务端仿真 App 并自动发短信 | 未成功，上游 `248` | 不适用 | 高 | 不作为默认方案。 |
| 远端 Android 模拟器 | 可保留官方运行环境 | 依赖设备持久化 | 很高，每用户需独立身份 | 技术可行但不适合常规部署。 |
| 本机 ADB 桥接 | 用户在官方 App 发码 | 可配合 refresh token | 中等，需要用户设备 | 仅在必须使用 App 短信时考虑。 |
| 保存 refresh token 并官方续期 | 不能解决首次登录 | 可解决常规 token 过期 | 低 | 应作为现有账号的默认策略。 |
| 官方扫码/OAuth | 当前 APK 未发现 | 取决于官方 | 低 | 若官方未来提供，应优先采用。 |

## 运营建议

避免因单个接口报错清空已有凭证。对凭证失效应区分“可刷新”和“必须重新授权”，并把上游返回码及不含敏感数据的错误说明展示给用户。

补充：截至 2026-07-31，字段和签名形态对齐后的服务器侧独立复测仍为 `248`。这说明不能仅靠修正历史协议偏差恢复服务器自动发码；是否可行还取决于官方是否接受非原生验证码回执、非持久化 Android 设备身份及非 Android TLS 环境。应把官方 App 的人工登录与 refresh token 续期作为当前可靠边界，而不是继续扩大服务端仿真或规避客户端校验。
