# DNA 资源解析与自适应下载设计

日期：2026-09-09

## 背景

当前插件存在两套同时使用的运行期素材树：

- `resources/`：由 `dna-resource` Git 仓库同步得到的公共资源目录。
- `resource/`：legacy 运行时按需下载缓存，包含 `avatar/`、`weapon/`、`paint/`、`skill/`、`mod/`、`attr/` 等目录。

实际检查发现，`resources/images/` 已包含一批角色头像、角色立绘和武器图，但角色面板和卡片渲染仍大量通过 legacy `resource/` 路径取图，因此即使管理员执行了“同步资源”，部分面板仍会在首次查询时联网下载同类素材。

此外，当前角色详情渲染中还存在多处串行等待：武器逐把处理、武器 Mod 逐个处理、角色 Mod 逐个处理、技能图逐个处理。`ImageFetcher` 虽然会合并相同 URL + 目标路径的并发请求，但没有全插件共享的自适应下载池，并且真实下载时会为每次请求新建 `httpx.AsyncClient`，无法充分复用连接。

这些行为共同导致冷缓存用户在执行面板或卡片命令时出现明显延迟。

## 目标

1. `dna-resource` 已同步且可直接使用的素材必须优先本地命中，不再重复联网下载。
2. 对无法提前穷举的长尾素材继续采用按需下载，不要求全部纳入 Git 资源仓库。
3. 所有运行期素材下载共享一个全插件自适应高并发池，而不是每张面板单独开池。
4. 把当前明显串行的独立素材请求改成批量并发准备，降低冷缓存首张卡片耗时。
5. 保留缓存校验、原子写入、请求合并和失败降级语义，不能以牺牲稳定性换速度。
6. 不向用户暴露固定并发数配置；并发由插件自动调节，并设置内部硬上限作为保险丝。

## 非目标

- 不把所有 Mod、技能图或未来可能出现的素材全部维护到 `dna-resource`。
- 不在“同步资源”阶段强制扫描并下载所有运行时长尾素材。
- 不复制或软链接 Git 同步资源到 legacy `resource/` 目录。
- 不为单次面板请求创建独立高并发下载池。
- 不改变现有资源同步的 generation 原子切换模型。

## 方案选择

评估过以下三种方案：

1. 仅修本地优先级，并把串行 `await` 改为 `asyncio.gather`。改动较小，但多人同时查询时缺少全局流控，也没有反馈式并发控制。
2. 本地优先 + 全局共享自适应下载池 + HTTP 连接复用。能够同时解决重复下载、串行 I/O 和多人并发失控问题。
3. 在方案 2 基础上，每次“同步资源”后自动预热长尾缓存。首次查询更快，但同步耗时、网络流量和维护复杂度明显增加，而且无法可靠预测全部 Mod 和技能素材。

采用方案 2。

## 总体架构

新增统一的运行期素材解析层，以下以 `AssetResolver` 作为概念名称；最终实现时可根据现有模块命名规范调整。

渲染代码不再直接决定“读哪个目录或是否联网”，而是通过统一解析接口请求具体素材。

资源读取优先级固定为：

1. `resources/`：Git 同步的公共资源，L1 本地资源。
2. `resource/`：运行期按需下载缓存，L2 本地缓存。
3. 全局共享下载池：网络获取缺失素材。
4. 下载成功后写入 `resource/`，供后续所有用户复用。

`resources/` 保持只读语义。网络下载只写 `resource/`，两套目录不再互相复制。

## 资源映射

第一阶段必须覆盖以下已能稳定映射的公共素材：

- 角色头像：`resources/images/role_avatar/<char_id>.png`。
- 角色立绘：`resources/images/role_paint/<char_id>.png`。
- 武器图：`resources/images/weapon/<weapon_id>.png`。

这些素材若在当前有效 resource generation 中存在且通过图片校验，则直接返回本地文件或已加载图像，不进入网络下载链路。

以下素材继续允许走 legacy 缓存和网络按需下载：

- Mod 图。
- 技能图。
- 属性、武器属性等未被 Git 公共资源完整覆盖的动态图标。
- 上游新增但当前 `dna-resource` 尚未收录的角色、武器或立绘。

若未来 `dna-resource` 新增了这些目录，可以扩展解析映射，但不要求本次设计一次性覆盖。

## AssetResolver 职责

统一解析层只负责以下职责：

1. 根据资源类型和 ID 生成候选本地路径。
2. 依次尝试 L1 公共资源与 L2 动态缓存。
3. 对候选图片执行现有完整性校验。
4. 本地均未命中时，提交下载任务到共享下载池。
5. 下载完成后返回动态缓存中的文件。
6. 可选素材下载失败时，由调用方沿用既有占位或隐藏语义。

它不负责：

- Git 同步。
- resource generation 的发布和切换。
- HTML/PIL 渲染。
- 决定某个业务区块是否应该隐藏。

这样可以把“素材从哪里来”与“卡片如何渲染”分离。

### 当前 generation 的读取约束

`AssetResolver` 不应自行缓存一个永久不变的 `resources/` 根路径。每次解析 L1 公共素材时，应通过现有 `ResourceSnapshotCoordinator` 或等价的 generation lease 取得当前已发布快照，并在本次素材读取/渲染所需的生命周期内保持该快照有效。这样“同步资源”完成后的 generation 切换可以自然生效，也不会出现长生命周期 resolver 一直读取旧 generation 的问题。

## 全局共享自适应下载池

所有运行期图片下载共享单个进程级调度器。

### 连接模型

- 使用一个长生命周期 `httpx.AsyncClient`。
- 复用 TCP/TLS 连接和连接池。
- 插件启动时初始化，插件停止或重载时显式关闭。
- 不再为每张图片创建新的 `AsyncClient`。

### 请求去重

保留当前 `ImageFetcher` 已有的“相同 URL + 相同目标路径共享一个真实下载任务”语义。

共享下载池位于去重后的真实下载路径上，因此多个玩家同时触发同一张图时：

1. 只会存在一个真实下载任务。
2. 其他等待者共享结果。
3. 单个等待者取消不会取消仍被其他调用方需要的下载。

### 自适应并发

采用 AIMD 风格的反馈控制：

- 健康窗口内没有 429、5xx、明显超时或连接异常时，逐步提高允许并发。
- 发生拥塞信号时快速降低并发，例如把当前窗口近似减半。
- 429 必须优先遵守 `Retry-After`。
- 5xx、超时和传输异常作为较弱拥塞信号累计处理，避免单次偶发错误导致剧烈振荡。
- 成功请求持续恢复后再逐步升高并发。

内部应设置较高但有限的硬上限，建议以 64 作为首个实现的保护值，作为保护上游与本机文件描述符/连接资源的保险丝。该数值属于内部实现参数，不提供给用户手动配置；后续只能依据真实压力测试结果调整，而不是让用户手工调参。

初始并发不应过低，应根据机器能力和客户端连接池能力给出积极但有限的起点；实际实现可结合 CPU 核心数、连接池上限等静态信号选择初始值，但运行中仍以网络反馈为主要调节依据。自适应控制的目标是提高 I/O 吞吐而不是追求最大并发数字，因此不能根据 CPU 核心数线性无限放大连接数。

并发控制实现不能简单依赖一个创建后固定容量的 `asyncio.Semaphore`。为了支持运行中升降并发，调度器应拥有可动态调整的容量状态，并保证缩容时不会中断已开始的请求，只限制后续任务进入；扩容则立即允许更多排队任务进入。

## 渲染前批量准备

高并发池只有在上层能同时提交独立任务时才能发挥作用，因此需要移除当前角色详情卡中的明显串行 I/O。

### 角色总览

当前总览条目已经在 section 层使用 `asyncio.gather`，应保留该结构，并让每个条目的素材读取统一经过 `AssetResolver`。

### 角色详情

角色详情卡在进入 HTML 渲染前，先并发准备所有互不依赖的远程素材：

- 角色立绘。
- 角色元素图标。
- 技能图。
- 角色 Mod 图。
- 3 把武器的武器图。
- 每把武器的 Mod 图。

3 把武器之间并发准备；每把武器内部各 Mod 也并发准备。

业务数据的顺序和最终渲染顺序保持不变，只改变素材 I/O 的等待方式。

### 并发边界

上层可以积极使用 `asyncio.gather` 提交任务，但真正的网络并发度由全局共享下载池控制。因此多个玩家同时查询时不会出现“每个请求各自开几十连接”的乘法式爆发。

## 失败与降级

### 本地公共资源损坏

若 `resources/` 中候选文件存在但图片校验失败：

1. 不直接让整张卡失败。
2. 记录安全日志，不泄露无关路径或响应正文。
3. 跳过该层，继续尝试 `resource/` 动态缓存。
4. 动态缓存也无效时再尝试网络下载。

公共资源目录保持只读，不在这里删除或覆盖坏文件。

### 动态缓存损坏

沿用现有行为：损坏的普通缓存文件可清理后重新下载，但必须保持符号链接安全检查。

### 网络失败

- 可选卡片素材继续允许返回内存占位图或隐藏对应可选元素。
- 严格依赖的素材按现有调用方语义抛出异常。
- 占位图不能写入缓存。
- 后续查询仍然允许重新尝试下载。

为了防止同一坏 URL 在多人并发时形成持续重试风暴，下载池可以对刚刚失败的相同请求保留一个很短的进程内失败冷却窗口；该窗口只能抑制瞬时重复请求，不能写入持久缓存，也不能阻止下一次正常查询在合理时间后重新尝试。

### 原子写入

继续使用临时文件写入、图片校验、`os.replace` 原子替换，避免并发读取到半成品文件。

## 与资源同步的关系

“同步资源”仍只负责 `dna-resource` Git 仓库：

1. clone 或 fast-forward 更新仓库。
2. 校验 manifest 与运行期目录。
3. 构建新的 resource generation。
4. 新 generation 完整有效后原子切换当前指针。

渲染器始终通过当前 generation 读取 `resources/`，因此同步过程中继续使用上一代完整资源，不读取正在更新到一半的目录。

同步完成后不需要复制资源到 `resource/`，也不主动批量预热所有长尾素材。

## 生命周期

共享下载组件必须具有明确生命周期：

### 启动

- 创建长生命周期 `AsyncClient`。
- 初始化自适应并发控制器。
- 初始化 in-flight 去重表。

### 运行

- 接收所有资源解析层提交的远程下载任务。
- 记录必要的健康指标，例如当前并发、成功数、拥塞信号数和最近一次缩容原因。

### 停止/重载

1. 标记停止接收新的下载任务。
2. 已存在共享任务允许按明确策略完成或被统一取消；实现时需选择一种一致语义并覆盖测试。
3. 消费任务异常，避免后台任务泄漏告警。
4. 关闭 `AsyncClient`。
5. 清理 in-flight 注册表。

不能让插件重载后残留旧连接池或旧任务。

## 可观测性

不要求新增用户侧配置，但应提供足够的日志或内部状态用于排查：

- L1 `resources/` 命中次数。
- L2 `resource/` 命中次数。
- 实际网络下载次数。
- 去重共享命中次数。
- 当前/最近自适应并发窗口。
- 429 / 5xx / timeout 等拥塞信号统计。

日志应避免输出敏感 URL 参数、凭据、响应正文等信息。

“资源状态”命令可在后续迭代中扩展为展示下载池状态，但不作为本次必须项。

为了避免日志本身成为高并发场景的性能负担，逐文件成功下载不应默认提升为高频用户可见日志；汇总统计、拥塞事件和异常才是主要观测信号。

## 兼容性

- 保留现有 `get_avatar_img`、`get_weapon_img`、`get_paint_img`、`get_mod_img`、`get_skill_img` 等函数的业务签名，优先在内部接入统一解析层，以降低改动面。
- 现有调用方对占位图和异常的语义应保持不变。
- 旧 `resource/` 缓存继续有效，无需迁移或清空。
- 管理员已有的“同步资源”命令语义不变，只是同步后的公共图片能够真正被角色卡优先使用。

## 测试设计

### 单元测试

至少覆盖：

1. `resources/` 存在有效图片时零网络调用。
2. `resources/` 缺失、`resource/` 命中时零网络调用。
3. 两层均缺失时进入下载池并写入动态缓存。
4. L1 图片损坏时回退 L2/网络，不修改 L1。
5. L2 图片损坏时按现有安全规则清理并重下。
6. 相同 URL + 目标并发请求只产生一个真实下载。
7. 不同 URL 能够被共享池并发执行。
8. 429 + `Retry-After` 会触发等待和并发收缩。
9. 连续健康请求会逐步恢复/提升并发。
10. 多次 5xx/timeout 会触发收缩，但单个偶发错误不造成过度振荡。
11. 插件关闭后 `AsyncClient` 被关闭，不能继续接收新任务。
12. 上层任务取消不会错误取消仍有其他等待者的共享下载。
13. generation 切换后新解析请求能够读取新快照，而旧 lease 在完成前仍保持一致视图。
14. 相同失败请求在短冷却窗口内不会形成重复下载风暴，冷却后仍允许重新尝试。

### 渲染测试

使用真实或等价复杂度数据覆盖：

- 多技能角色。
- 9 个角色 Mod。
- 3 把武器。
- 武器各自包含多个 Mod。

验证最终卡片内容、顺序和资源数量与优化前一致。

### 冷缓存性能验证

1. 保留完整 `resources/` 当前 generation。
2. 清除目标角色相关的 `resource/` 动态缓存。
3. 渲染复杂角色详情卡并记录总耗时、实际网络请求数、最大活跃下载数。
4. 与改造前相同场景对比。
5. 再执行第二次请求，确认基本全部本地命中，耗时接近纯渲染时间。

### 多用户压力验证

同时发起 5 到 10 个不同角色的冷缓存请求：

- 所有请求共享同一个下载池。
- 活跃网络请求不超过内部硬上限。
- 没有每个请求独立倍增连接数的现象。
- 若上游返回 429 或明显超时，观察到并发自动收缩并在恢复后逐步回升。

### 离线验证

断开外网后验证：

- `dna-resource` 已包含的角色头像、立绘、武器图能够继续正常使用。
- 只有真正缺失的长尾素材降级为占位或隐藏。
- 不因为网络不可用导致整张本可由本地资源完成的卡片失败。

## 验收标准

本设计完成后，应满足：

1. `dna-resource` 当前 generation 已有的角色头像、立绘和武器图在面板渲染中零网络获取。
2. 同步公共资源后不再因为 legacy 路径割裂而重复下载已有公共素材。
3. 角色详情中的武器、Mod、技能等独立资源不再按当前结构串行等待。
4. 所有运行期下载共享同一个全局自适应并发池。
5. 正常网络条件下并发会主动提高；出现 429、5xx、timeout 等拥塞信号时会自动回压。
6. 多用户并发查询不会按“用户数 × 单请求并发”无限放大连接数。
7. 动态缓存仍使用原子写入和图片完整性校验。
8. 可选素材失败时不会写入假缓存，后续仍可重试。
9. 插件停止/重载不会遗留旧 `AsyncClient` 或孤儿下载任务。
10. 冷缓存复杂面板的首张卡片耗时应显著低于优化前；第二次查询应接近纯本地渲染耗时。

## 实施边界建议

实现阶段建议按以下模块边界推进：

1. 先把长生命周期 HTTP 客户端、请求去重和自适应并发控制收敛到独立下载组件。
2. 再增加统一 `AssetResolver`，先接角色头像、立绘、武器三类 L1 公共资源映射。
3. 保持旧图片获取函数签名，在内部改为调用解析层。
4. 最后重构角色详情 payload 构建，把可并行的素材准备转换为批量并发。

这样每一步都可以独立测试和回滚，避免同时改资源来源、网络层和渲染结构导致问题难以定位。
